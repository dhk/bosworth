# Session Event Registry v0.1

**Status:** Draft for review  
**Scope:** Deliberately minimal  
**Purpose:** Test whether sessions and human interactions can be observed consistently across AI clients and devices.

## 1. Objective

Build the smallest possible shared registry that can answer:

1. Did a session start?
2. Is the session still alive?
3. Did a human interaction occur in that session?
4. Did the session end?

The registry does **not** attempt to understand, remember, summarize, or store the content of the conversation.

This is an instrumentation layer, not a memory system.

The design is intentionally narrow so that each assumption can be tested against real surfaces such as Claude.ai, Claude on iPhone, Claude Desktop, and Claude Code before building anything more ambitious.

## 2. Example

A user opens an AI session and says:

> Hello Bosworth.

The AI responds:

> Hello Angel.

The registry should be able to establish:

- a session existed;
- the session started at a particular time;
- a human interaction occurred;
- the AI produced a response;
- the interaction belonged to that session;
- the session subsequently remained active or ended.

The registry does **not** need to store `"Hello Bosworth"` or `"Hello Angel"`.

A minimal event sequence might be:

```text
SESSION_STARTED
INTERACTION_OCCURRED
SESSION_HEARTBEAT
SESSION_ENDED
```

## 3. Non-goals

Version 0.1 does not provide:

- conversational memory;
- transcript storage;
- prompt or response capture;
- semantic extraction;
- decisions;
- summaries;
- embeddings;
- entity resolution;
- cross-session context injection;
- synchronization of Claude's native memory;
- inference about what a session is working on;
- inference about whether two sessions concern the same project.

Those capabilities may eventually consume this registry, but they are explicitly outside this design.

## 4. Core model

The registry is an append-only stream of **session events**.

An event records an observable fact:

```text
Something happened
at this time
in this session
on this client.
```

The authoritative data is the event stream.

Current session state is derived from those events.

## 5. Event types

### 5.1 `SESSION_STARTED`

Emitted when an observable AI session begins.

```json
{
  "event_id": "01K...",
  "event_type": "SESSION_STARTED",
  "occurred_at": "2026-09-05T16:42:03.218-07:00",
  "session_id": "claude-code:4f92...",
  "source": {
    "product": "claude-code",
    "surface": "desktop",
    "device_id": "macbook-dhk"
  }
}
```

### 5.2 `SESSION_HEARTBEAT`

Indicates that the producer still considers the session alive.

```json
{
  "event_id": "01K...",
  "event_type": "SESSION_HEARTBEAT",
  "occurred_at": "2026-09-05T16:43:03.218-07:00",
  "session_id": "claude-code:4f92...",
  "source": {
    "product": "claude-code",
    "surface": "desktop",
    "device_id": "macbook-dhk"
  }
}
```

A heartbeat is useful where the underlying product does not expose a reliable session-ended signal.

### 5.3 `INTERACTION_OCCURRED`

Records that a human-to-AI interaction occurred.

It records **the existence and mechanics of the interaction, not its semantic content**.

```json
{
  "event_id": "01K...",
  "event_type": "INTERACTION_OCCURRED",
  "occurred_at": "2026-09-05T16:44:12.105-07:00",
  "session_id": "claude-code:4f92...",
  "interaction_id": "01K...",
  "source": {
    "product": "claude-code",
    "surface": "desktop",
    "device_id": "macbook-dhk"
  },
  "payload": {
    "human_input_observed": true,
    "assistant_output_observed": true
  }
}
```

Optional mechanically observable metadata may later include:

```json
{
  "input_bytes": 15,
  "output_bytes": 11,
  "response_duration_ms": 842
}
```

These fields must not be required for a producer that cannot observe them.

### 5.4 `SESSION_ENDED`

Emitted when the producer can positively observe that a session ended.

```json
{
  "event_id": "01K...",
  "event_type": "SESSION_ENDED",
  "occurred_at": "2026-09-05T17:02:51.003-07:00",
  "session_id": "claude-code:4f92...",
  "source": {
    "product": "claude-code",
    "surface": "desktop",
    "device_id": "macbook-dhk"
  }
}
```

A missing `SESSION_ENDED` event must **not** be interpreted as proof that a session is still running.

## 6. Required event envelope

Every event must contain:

| Field | Meaning |
|---|---|
| `event_id` | Globally unique identifier generated by the producer |
| `event_type` | One of the defined event types |
| `occurred_at` | Time observed by the producer |
| `session_id` | Stable identifier for the observed session |
| `source.product` | Product producing the session |
| `source.surface` | Relevant client/surface |
| `source.device_id` | Stable local device identifier when available |

The registry should additionally record its own ingestion timestamp:

```json
{
  "received_at": "2026-09-05T23:44:12.241Z"
}
```

`occurred_at` and `received_at` are intentionally separate because clients can be offline, clocks can differ, and events can arrive late.

## 7. Session identity

`session_id` is the critical integration problem.

Whenever a product exposes a stable native conversation/session identifier, the producer should use or deterministically incorporate it.

If no native identifier is available, the producer may generate one:

```text
<producer>:<generated-uuid>
```

A locally generated ID identifies **the observer's notion of a session**. It must not be represented as the product's canonical session identifier unless that has been verified.

## 8. Storage

The initial implementation can use SQLite.

```sql
CREATE TABLE session_events (
    event_id TEXT PRIMARY KEY,
    event_type TEXT NOT NULL,
    occurred_at TEXT NOT NULL,
    received_at TEXT NOT NULL,
    session_id TEXT NOT NULL,
    product TEXT NOT NULL,
    surface TEXT NOT NULL,
    device_id TEXT,
    interaction_id TEXT,
    payload_json TEXT
);

CREATE INDEX idx_session_events_session
    ON session_events(session_id, occurred_at);

CREATE INDEX idx_session_events_time
    ON session_events(occurred_at);
```

Rows are immutable after insertion.

Duplicate delivery is handled through the unique `event_id`.

## 9. Minimal interface

The registry needs only three logical operations.

### Record an event

```http
POST /events
```

### Inspect a session

```http
GET /sessions/{session_id}/events
```

### List recently active sessions

```http
GET /sessions/active
```

“Active” is derived state rather than a stored fact:

```text
active =
    SESSION_STARTED exists
    AND no subsequent SESSION_ENDED exists
    AND latest observed activity is within the configured timeout
```

The timeout is an operational policy, not a statement about the underlying AI product.

## 10. Producer contract

Each integration is a **producer**.

```text
Claude.ai web
        |
        v
   Web producer
        |
        |
Claude Code ---- CLI producer
        |
        |
Claude Desktop - Desktop producer
        |
        |
Claude iPhone -- iOS producer (if technically possible)
        |
        v
+-----------------------+
| Session Event Registry|
+-----------------------+
        |
        v
    append-only
     event store
```

A producer has only three responsibilities:

1. determine that an observable event occurred;
2. associate it with a session;
3. deliver the event to the registry.

The producer does not perform memory extraction.

## 11. Delivery behavior

Session operation must never depend on registry availability.

If the registry cannot be reached:

1. the producer continues operating;
2. events may be queued locally where the integration permits it;
3. queued events are retried later;
4. original `event_id` and `occurred_at` values are retained.

This gives the registry **at-least-once delivery semantics** where durable local queuing is possible.

The server uses `event_id` to make duplicate delivery harmless.

Where a surface does not permit durable interception or local queuing, the system must explicitly accept possible event loss rather than claim stronger guarantees.

## 12. Ordering

Global event ordering is not assumed.

Events can arrive late or out of order. Consumers use `occurred_at` for observed chronology while retaining `received_at` for debugging and reconciliation.

No claim is made that client clocks are perfectly synchronized.

## 13. Privacy boundary

The v0.1 registry records metadata.

It should be possible to inspect the event store and learn:

```text
At 16:44, a human interacted with Claude Code on device X.
```

It should **not** be possible to learn from this registry:

```text
The human said "Hello Bosworth."
Claude replied "Hello Angel."
```

A future transcript or memory system should be a separate component with a separate data contract and privacy policy.

## 14. Failure cases that must be visible

The design must not hide uncertainty.

**Missing start:** An interaction may be recorded, but the registry must not invent a start event.

**Missing end:** The session eventually becomes `stale`, not definitively `ended`.

**Duplicate event:** The second insert is ignored because `event_id` already exists.

**Late event:** It retains its original `occurred_at` and receives the current `received_at`.

**Unknown interaction completion:** The registry records which side of the interaction was actually observed.

```json
{
  "human_input_observed": true,
  "assistant_output_observed": false
}
```

## 15. The key claim to test

This design deliberately does **not** assume that every Claude surface provides the hooks necessary to produce these events.

For each target surface, we need evidence for:

| Surface | Start observable? | Interaction observable? | End observable? | Stable session ID? | Can emit externally? |
|---|---:|---:|---:|---:|---:|
| Claude Code CLI | TBD | TBD | TBD | TBD | TBD |
| Claude Code/Desktop | TBD | TBD | TBD | TBD | TBD |
| Claude.ai web | TBD | TBD | TBD | TBD | TBD |
| Claude on iPhone | TBD | TBD | TBD | TBD | TBD |

A proposed integration is not viable until these cells are populated from documentation, experimentation, or both.

In particular, the architecture must **not** assume that an arbitrary Claude iPhone conversation can directly call a custom event bus or MCP server. That capability must be demonstrated.

## 16. Acceptance test

The first end-to-end test contains no memory functionality.

1. Start an instrumented session.
2. Registry receives `SESSION_STARTED`.
3. Human says `"Hello Bosworth."`
4. AI responds `"Hello Angel."`
5. Registry receives one `INTERACTION_OCCURRED`.
6. Continue or wait long enough to observe a heartbeat.
7. End the session where an explicit end can be detected.
8. Registry receives `SESSION_ENDED`, or the session becomes `stale` if no end signal is available.

Expected registry history:

```text
16:42:03 SESSION_STARTED
16:44:12 INTERACTION_OCCURRED
16:45:03 SESSION_HEARTBEAT
17:02:51 SESSION_ENDED
```

The event database must contain neither `"Hello Bosworth"` nor `"Hello Angel"`.

## 17. Review questions

This document should be reviewed primarily by trying to disprove its assumptions:

1. Can each target surface actually be instrumented?
2. What does “session started” mean on each surface?
3. Can we obtain a stable session identifier?
4. Can we reliably distinguish one interaction from streaming or intermediate model activity?
5. Can we detect an explicit session end?
6. Where can events be emitted directly?
7. Where is a wrapper, extension, proxy, filesystem watcher, hook, or other observer required?
8. Which integrations cannot provide durable delivery?
9. What permissions or security boundaries prevent observation?
10. Does instrumentation violate any product terms, platform restrictions, or user privacy expectations?
11. Can the same logical conversation move between devices, and if so, how is identity preserved?
12. Which claims are product-independent, and which depend specifically on Claude's current implementation?

## 18. Success criterion for v0.1

Version 0.1 succeeds if, for every supported surface, another process can establish:

> **A session existed, and human interaction occurred within it.**

Nothing more is required.

Only after that claim is demonstrated across the desired surfaces should this registry be used as a foundation for shared context, cross-session awareness, or memory.
